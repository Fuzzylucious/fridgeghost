# How Kiro Was Used — FridgeGhost

An honest account of Kiro's role in building this project, written for the
Kiroween 2026 submission. Nothing here is embellished: what Kiro did, what it
did not do, and what was done by hand instead.

## What actually happened

### Kiro CLI was installed and verified

Kiro CLI **3.2.0** was installed on the build VM via the official installer:

```bash
curl -fsSL https://cli.kiro.dev/install | bash
```

Verified after installation:

```bash
$ kiro-cli --version
3.2.0

$ kiro-cli whoami
Not logged in
```

### The Kiro agent itself could NOT run in this build session

Sign-in to Kiro requires **interactive browser OAuth as the user** — GitHub,
Google, or AWS Builder ID — and no user credentials were available to the
builder in this unattended session. There was no way to authenticate the agent
without the user completing the browser sign-in flow themselves, so the Kiro
agent never executed a single step of this build. No spec was generated by
Kiro, no code was written by Kiro, no hook was fired by Kiro.

### What was done instead: Kiro's spec-driven format, by hand

The build followed Kiro's **spec-driven development** workflow manually, so
the repository is Kiro-ready and the user can pick it up in the Kiro IDE or
Kiro CLI and continue with the agent:

1. **Requirements** — `.kiro/specs/fridgeghost/requirements.md`:
   EARS-style requirements ("WHEN ... THE SYSTEM SHALL ...") with acceptance
   criteria, covering manual entry, barcode lookup, expiry warnings, recipe
   suggestions, shopping list, local-first storage, one-command run, plus
   non-functional requirements (no paid keys, no accounts, no data leaves
   the machine, graceful API failure).
2. **Design** — `.kiro/specs/fridgeghost/design.md`: architecture and
   components, data flow, full API contract, error handling, testing approach.
3. **Tasks** — `.kiro/specs/fridgeghost/tasks.md`: a sequenced implementation
   checklist. Items are marked done only where the file was verified to exist
   on disk; everything else is left unchecked for the next session.
4. **Steering** — `.kiro/steering/product.md` (vision and tone),
   `.kiro/steering/tech.md` (stack, TypeScript strict, free APIs only, no
   secrets), `.kiro/steering/structure.md` (repo layout, file ownership, API
   shapes).
5. **Hooks** — `.kiro/hooks/hooks.json`: a pre-commit hook that runs
   `npm run build` (typecheck), a hook reminding the agent never to commit
   secrets, and a best-effort scan of staged changes for credential-like
   values.

The implementation itself (server, API clients, frontend) was written by
human-directed builders following those specs — not by the Kiro agent.

## What Kiro did

- Nothing at runtime. The Kiro CLI binary (3.2.0) was installed and its
  version / login state verified.
- Kiro's **format and conventions** shaped the repo: the spec → design →
  tasks flow, the steering docs, and the hooks config are all laid out the
  way Kiro expects them, so the project opens cleanly in Kiro.

## What Kiro did not do

- Kiro did not write any code in this repo.
- Kiro did not generate any spec, design, or task list — those were written
  by hand following Kiro's documented format.
- Kiro did not run any hooks, builds, or tests.
- Kiro was not authenticated at any point during this build (`whoami`:
  "Not logged in").

## How to continue with Kiro

1. Open this repo in the Kiro IDE, or run `kiro-cli` and complete the
   browser sign-in (GitHub / Google / AWS Builder ID).
2. The specs are at `.kiro/specs/fridgeghost/` — ask Kiro to implement the
   unchecked items in `tasks.md`, starting with Phase 7 (smoke test,
   failure-mode check, one-command check from a clean checkout).
3. Steering docs in `.kiro/steering/` tell the agent the product rules
   (local-first, free APIs only, no secrets) without needing to repeat them.
4. The hooks in `.kiro/hooks/hooks.json` run `npm run build` before commits
   and guard against secrets entering the repo.

## Bottom line

Kiro the product shaped how this repo is organised; Kiro the agent did not
build it, because interactive sign-in was not possible in this unattended
session. The repo is structured so the agent can take over from here.
